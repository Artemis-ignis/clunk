현재는 실제로 작동하는 MVP를 만들어 검증하고 있습니다. GLB 파일의 바이트를 직접 읽어 해시·구조·메트릭을 계산하고, 정책 기준과 비교해 Game-Ready Score를 산출하며, 허용된 범위의 최적화를 새 파일로 만들어 다시 검사하고, 전후 해시를 Asset Passport로 남기는 흐름이 웹 브라우저에서 동작합니다. 여기에 제가 개발 중인 게임의 실제 런타임 GLB 8개(기계 4종의 근거리·원거리 LOD)를 읽기 전용으로 검사해, 실전 파이프라인을 거친 파일에서도 검사가 그대로 동작한다는 점과 범용 정책만으로는 프로젝트별 규칙을 대체할 수 없다는 점을 함께 확인했습니다.

【Q3-1. 기존 제품 및 서비스 대비 차별점과 어떤 문제를 해결할 수 있나요? (2000자)】 — 1604자
----------------------------------------
해결하는 문제는 "3D 에셋을 게임에 넣기 전에 품질·호환성·성능 위험을 확인하고 그 근거를 남기는 일"입니다. 지금 이 일은 3D 뷰어에서 눈으로 확인하고, 엔진에 임포트해서 오류가 나면 되돌리고, 문제가 반복되면 담당자가 경험으로 걸러내는 방식으로 처리됩니다. 결과가 파일 단위로 기록되지 않고, 원본과 수정본의 차이를 재현할 수 없으며, 검수 기준이 사람마다 다릅니다.

기존 도구와의 차이는 세 축입니다.

첫째, 실제 파일 바이트를 기준으로 측정합니다. 표준 검증 도구(glTF Validator 등)는 파일이 포맷 명세를 지키는지를 봅니다. 명세를 지킨 파일도 삼각형이 수십만 개이거나 머티리얼이 수십 개면 게임에서는 문제가 됩니다. Clunk는 GLB/GLTF 바이트를 직접 읽어 삼각형·정점 수, 머티리얼·드로우 콜, 텍스처 해상도와 메모리, 빈 노드, 비정상 스케일, normal·UV 누락 같은 실전 지표를 계산하고, 정책 기준값과 비교해 finding과 Game-Ready Score로 만듭니다.

둘째, 허용 목록에 있는 작업만 새 파일로 적용합니다. 변환·압축 도구(gltf-transform, Draco 등)는 파일을 바꿔 주지만 "바꾼 결과가 안전한지"는 확인해 주지 않습니다. Clunk는 원본을 덮어쓰지 않고, 허용 목록 작업(빈 노드 제거, 중복 머티리얼 정리, 명시한 비런타임 메타데이터 정리, 별도 파일 재패킹)만 새 파일로 적용합니다. mesh 단순화, 텍스처 재인코딩, 애니메이션 변경처럼 형상이나 표현을 바꿀 수 있는 작업은 자동 적용하지 않아 안전 경계가 분명합니다.

셋째, 출력 파일을 다시 검사해 증거로 남깁니다. 최적화 성공 문구가 아니라, 새로 만든 파일을 처음부터 다시 파싱·검사한 결과로 증명합니다. 입력·출력 파일의 SHA-256 해시, 규칙 세트 ID와 버전, 적용한 작업 목록, 전후 메트릭과 점수, 전후 검사 리포트의 digest를 Asset Passport로 기록합니다. 같은 파일에 같은 정책을 적용하면 항상 같은 결과가 나온다는 점은 자동 테스트로 확인했습니다.

이 세 축이 만드는 효과는 절약한 시간이나 비용이 아니라 의사결정의 근거입니다. 나중에 문제가 생겼을 때 "이 파일을 왜 통과시켰는가"를 입력·출력 해시, 정책 버전, finding, 전후 메트릭으로 파일 단위로 되짚을 수 있습니다.

세 축은 화면 하나에만 있지 않습니다. 웹 화면, CLI, AI 에이전트용 MCP 서버, VS Code 확장이 같은 검사 엔진을 호출합니다. CLI와 MCP가 내놓는 결과가 검사 엔진의 결과와 완전히 일치하는지, VS Code 확장이 같은 CLI 계약을 사용하는지를 자동 테스트로 검증하고 있습니다. AI 코딩 에이전트가 에셋을 만든 직후 스스로 검사를 호출하는 파이프라인은 이 구조 위에서 가능한 이후 확장 방향이며, 현재 확보한 사실은 위 자동 테스트가 검증하는 범위까지입니다.

원본 파일은 사용자의 브라우저 안에서 처리하고 서버로 자동 업로드하지 않습니다. 서버에는 검사 이력·해시·점수 같은 메타데이터만 저장합니다. 외주·미공개 프로젝트 에셋을 다루는 팀에게는 파일이 어디로 가는지가 도입 검토의 첫 질문이 될 것이라고 판단해 이 구조를 택했고, 보안 효과 자체를 측정한 단계는 아닙니다.

사업화는 이 기반 위에서, 단계마다 하나의 검증 질문에 답하는 방식으로 진행합니다. 아래 수치는 확보한 성과가 아니라 목표(가설)이며, 지금 확정된 파일럿 접점이나 전환 근거는 없습니다.

1단계(선정 후 1~3개월) — 검증 질문: 게임 팀이 에셋 검사를 반복 업무로 인식하고 도구를 다시 쓰는가. 1차 대상은 외주·마켓 에셋을 반복해서 통합하는 인디·소규모 게임 개발팀이라는 한 고객군으로 좁힙니다. 국내 게임 개발 커뮤니티, 인디 게임 행사, 게임 개발 스터디에서 접점을 만드는 일이 이 단계의 첫 과제이고, 파일럿 10팀 내외는 확보된 접점이 아니라 목표(가설)입니다. 측정 지표는 팀당 반복 사용률과 "검사 결과를 믿고 의사결정에 썼는가"입니다.

2단계(3~6개월) — 검증 질문: 지불 의사가 어떤 단위에 생기는가(월 구독인가, 검사 크레딧인가, 납품 증빙 Passport인가). 파일럿 데이터로 가격 가설을 좁히고 국내 결제를 연결합니다. 첫 유료 워크스페이스 확보는 이 단계의 목표(가설)입니다. 이 시점에 사업자 등록을 완료하고(현재 예비창업자), 창업활동자금은 결제 연동, 서버 재검증 인프라, 초기 고객 발굴에 배정합니다.

3단계(6~12개월) — 검증 질문: 어떤 정책·엔진 요구가 실제로 반복되는가. 파일럿에서 반복 확인된 요구부터 팀 정책 관리, CI/CD 연동, Unity·Unreal 등 엔진별 검사 프로파일, 서버 측 재검증과 Passport 보관을 추가해 팀·기업 플랜을 만듭니다.

외부 연동은 현재 사실과 이후 가설을 나눠 둡니다. 현재 사실은 CLI와 MCP 서버가 이미 동작해 외부 도구나 AI 에이전트가 같은 검사 엔진을 호출할 수 있다는 점입니다. 생성형 3D 도구 회사와의 제휴(생성 직후 자동 검사)와 에셋 마켓 검수 연동은 상대의 협조와 연동 계약이 전제되는 조건부 확장이며, 현재 논의 중이거나 합의된 상대는 없습니다.

세 질문의 답이 확인되면 확장 투자와 채용을 진행하고, 확인되지 않으면 데이터가 가리키는 인접 문제(예: 납품 검수 증빙 특화)로 빠르게 방향을 조정합니다.

【Q4-2. 책임멘토를 통해 어떤 도움을 받고 싶은가요? (2000자)】 — 930자
----------------------------------------
기술 구현은 실작동 MVP까지 스스로 진행했습니다. 지금 필요한 것은 기술이 아니라 사업 검증의 속도와 정확도를 높이는 도움이고, 우선순위는 두 가지입니다.

첫째(최우선), 첫 고객 발굴입니다. 1차 대상은 외주·마켓 에셋을 반복해서 통합하는 인디·소규모 게임 개발팀입니다. 이들에게 닿는 현실적인 채널(게임 관련 협회, 인디 게임 행사, 퍼블리셔 네트워크, 지역 게임 지원기관)을 소개받고, B2B 개발 도구를 처음 파는 창업자가 흔히 저지르는 실수를 미리 배우고 싶습니다. 멘토와 함께 실제 파일럿 팀 한 곳을 만들어 보는 것이 이 요청의 구체적인 목표입니다.

둘째, 가격 인터뷰 설계입니다. 구독과 사용량 크레딧을 결합한 모델에서 무엇을 어떻게 물어야 지불 의사를 과대평가하지 않는지, 어떤 팀을 인터뷰 대상에서 제외해야 하는지(예: 외부 에셋을 거의 쓰지 않는 팀, 이미 자체 검증 파이프라인을 운영하는 팀)를 국내 소규모 팀의 지불 관행을 아는 분의 관점으로 점검받고 싶습니다. 파일럿 설문·인터뷰 문항을 실제로 돌리기 전에 검토받는 것이 목표입니다.

다음 순위로는 두 가지가 있습니다. 하나는 예비창업자의 사업자 등록 시점 판단과 계약 실무(소프트웨어 이용약관, 개인정보 처리방침, 외주 에셋을 다루는 서비스의 책임 범위, 결제 사업자 연동 계약)이고, 다른 하나는 이후 이어질 창업 지원 사업(예비창업패키지 등)과의 로드맵 설계입니다. 두 가지 모두 앞의 두 우선 과제를 미루지 않는 선에서 도움받고 싶습니다.

멘토링에는 매 회차 데이터를 가지고 참여하겠습니다. 다만 파일럿 팀 수, 반복 사용률, 검사 건수, 문제 유형 분포는 지금 가지고 있는 데이터가 아니라 파일럿을 시작해야 얻는 향후 측정할 데이터입니다. 첫 회차에는 모집 진행 상황과 검증 질문을 가지고 가고, 이후 회차부터 측정값을 가지고 다시 검증받는 방식으로 진행하고 싶습니다.

## 제출용 아이디어 한 줄

**Clunk는 생성형·마켓·외주 게임 에셋의 실제 GLB/GLTF 바이트를 검사하고, 안전한 최적화와 재검사 결과를 Asset Passport로 남겨 개발자가 안심하고 게임 파이프라인에 넣도록 하는 Game AssetOps SaaS입니다.**

### 1. 해결하려는 문제

생성형 AI와 3D 마켓·외주 활용이 늘면서 게임 팀은 짧은 시간에 더 많은 에셋을 확보할 수 있게 되었습니다. 그러나 생성되거나 전달된 GLB/GLTF가 곧바로 게임에 넣을 수 있는 상태라는 보장은 없습니다. 불필요한 노드, 중복 머티리얼, 과도한 텍스처, 누락된 normal·UV, 비정상 transform, 큰 파일과 높은 draw call이 프로젝트 성능·호환성·검수 비용으로 돌아옵니다.

현재 소규모 팀은 Blender와 엔진에서 파일을 수동 확인하거나 담당자의 경험에 의존합니다. 결과가 파일별로 기록되지 않고 원본과 수정본의 차이를 재현하기도 어렵습니다. AI가 에셋을 빠르게 만드는 시대에는 생성 자체보다 **게임에 넣어도 되는지를 설명할 수 있는 품질 경계**가 필요합니다.

### 2. 제안하는 해결책

Clunk는 원본을 브라우저에서 처리하는 local-first AssetOps 워크스페이스입니다.

1. 사용자가 GLB/GLTF를 선택하면 실제 바이트, 파일 크기와 SHA-256을 계산합니다.
2. scene/node/depth, geometry, material, texture, animation/skin, bounds와 transform 메트릭을 수집합니다.
3. 버전이 고정된 정책의 threshold와 비교해 finding, severity, observed value와 Game-Ready Score를 만듭니다.
4. 원본을 덮어쓰지 않고 허용된 작업만 적용해 새 파일을 생성합니다.
5. 새 출력 파일을 다시 파싱하고 전후 해시·메트릭을 비교합니다.
6. 입력·출력 hash, 규칙 세트, 결과 digest, 작업을 Asset Passport JSON과 워크스페이스 이력으로 남깁니다.

현재 v1은 빈 identity 노드 제거, 동일 머티리얼 dedupe, 명시적으로 허용한 `extras`·`asset.generator`·`asset.copyright` metadata 정리와 별도 파일 repack만 자동 적용합니다. metadata 정리는 렌더 데이터가 아닌 항목만 제거하며 Passport에 `metadata-only` 작업으로 기록합니다. mesh simplification, texture 재인코딩, Draco/Meshopt, animation·skin 변경은 자동화하지 않아 안전 경계를 명확히 했습니다.

### 3. 차별성·기술성

- **수치의 출처가 실제 파일**: 화면에 하드코딩한 통계가 아니라 동일한 Core가 선택된 바이트에서 계산합니다.
- **최적화 뒤 재검사**: 최적화 버튼의 성공 문구가 아니라 새 결과물의 파싱·hash·메트릭으로 결과를 확인합니다.
- **설명 가능한 점수**: 정책 ID·버전, rule ID, 관측값, 기준값, severity와 digest를 함께 보존합니다.
- **원본 보존과 개인정보 경계**: 원본은 브라우저에 남기고 D1에는 계정·workspace·작업 메타데이터와 증거만 저장하며 원본 바이트는 저장하지 않습니다.
- **개발 도구로 확장 가능한 공통 Core**: Web뿐 아니라 CLI·MCP·VS Code가 같은 TypeScript Core 계약을 사용합니다.
- **제품 표면의 확장성**: Codex Plugin과 Clunk AssetOps Skill이 같은 계약과 안전 경계를 라우팅하며, MCP stdio 서버를 실제로 연결할 수 있습니다. 즉, Web 화면만 만든 것이 아니라 개발 도구·에이전트가 같은 검사 결과를 호출하는 구조입니다.
- **재현성**: 동일 입력·동일 정책이면 결과 digest가 동일하도록 canonical 결과를 사용합니다.

### 4. 고객과 사용 장면

초기 고객 후보는 다음과 같습니다.

- 3D 에셋을 반복적으로 만드는 인디·소규모 게임 스튜디오
- 외주·마켓 에셋을 받아 엔진 프로젝트에 통합하는 개발팀
- 생성형 3D 파이프라인을 운영하면서 산출물 품질을 확인해야 하는 AI 도구팀
- CI/CD 또는 AI coding agent에서 에셋 검사를 자동화하려는 기술팀

사용자는 Web에서 파일을 검사하거나, 개발자는 CLI·MCP·VS Code에서 같은 Core 검사·최적화 계약을 호출합니다. workspace 저장·크레딧 원장은 Web/Sites API가 담당합니다. 초기에는 파일럿 워크스페이스와 사용량 기반 크레딧을 검토하고, 이후 팀 정책·보관·CI 기능을 결합한 구독형 SaaS로 확장합니다. 현재 매출·유료 고객·시장 점유율은 확보했다고 주장하지 않습니다.

### 5. 사업화 방식

1차 데모는 실제 결제가 아닌 D1 데모 원장입니다. 검사와 최적화가 성공적으로 저장될 때만 크레딧을 차감하고, invalid/no-credit 작업은 원자적으로 무차감·무기록 처리하며, 데모 플랜 전환은 idempotent하게 처리합니다. 실제 사업 단계에서는 워크스페이스 구독, 사용량 크레딧, 팀 정책과 CI 연동을 조합하고 국내 결제 제공자를 분리된 `BillingProvider` 뒤에 연결합니다.

### 6. 현재 단계와 검증 결과

현재는 제품 MVP와 실증 준비 단계입니다.

- 실제 GLB 샘플 2종을 생성하고 출처·라이선스·hash를 기록했습니다.
- 문제 샘플을 동일 Core로 검사해 실제 finding과 score를 계산했습니다.
- 허용 목록 최적화 후 새 GLB를 만들고 새 파일을 다시 검사했습니다.
- Passport에 원본·출력 hash와 전후 결과를 포함했습니다.
- Web Inspector에서 3D 미리보기, finding, 최적화, 다운로드를 확인했습니다.
- CLI·MCP·VS Code가 같은 Core 계약을 사용하도록 구성했습니다.
- typecheck, lint, Core 테스트, production build와 브라우저 흐름을 실행했습니다.

위 항목은 `docs/application/evidence-matrix.ko.md`, `docs/application/verification-log.ko.md`와 `output/application/evidence/`에서 실행 증거와 연결합니다. 측정하지 않은 고객 수·매출·성능 수치는 신청서에 적지 않습니다.

### 7. 1차 서면 심사(1R) 이후 실행 계획

- 실제 사용자 에셋을 원본 보존 조건으로 받아 익명화된 정책 요구와 오류 유형을 수집합니다.
- 일반·기술트랙에 맞춘 멘토링을 통해 Web·Mobile·PC 및 Unity·Unreal·Godot별 정책 우선순위를 검증합니다.
- 현재 허용 목록 기반 작업의 안전성을 늘리고, 어떤 변경을 자동화하지 말아야 하는지도 함께 검증합니다.
- 사용자 인터뷰와 반복 작업 데이터를 바탕으로 유료 고객이 지불할 단위가 구독인지 사용량인지 확인합니다.
- R2 기반 서버 재검증이 필요한 고객군과 local-first로 충분한 고객군을 구분합니다.

### 사실·계획·가설 구분

- **측정된 사실**: 특정 입력 파일을 현재 로컬에서 실행해 얻은 hash·크기·메트릭·finding·score·재검사 결과만 `현재 검증 결과`로 표시합니다. 이 값은 특정 샘플의 파일 결과이며 고객 수·매출·제품 전체 성능을 뜻하지 않습니다.
- **계획**: `1차 서면 심사(1R) 이후 실행 계획`과 같이 앞으로 수행할 파일럿·인터뷰·기술 고도화는 계획형 문장으로 작성합니다.
- **가설**: 초기 고객 후보, 구독·크레딧 가격 단위, 서버 재검증 수요는 아직 검증 전인 가설 또는 검토 대상이며 실적처럼 쓰지 않습니다.
